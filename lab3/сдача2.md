## Общая идея алгоритмов — почему они работают

### Какую задачу вообще решаем

Математическая прямая может проходить через дробные координаты, например (2; 0,8). А центр пикселя может быть только в целой точке: (2; 0), (2; 1) и так далее. Поэтому нужно заменить непрерывную линию последовательностью клеток, которая проходит как можно ближе к ней.

Для пологой линии удобно идти по столбцам: в каждом следующем столбце выбирать ближайшую строку. Для крутой — наоборот, идти по строкам и выбирать столбец. **Главная ось — та, вдоль которой отрезок длиннее.** Если всегда делать по ней один шаг, по второй оси идеальная линия сдвинется не больше чем на одну клетку. Поэтому соседние выбранные пиксели будут соприкасаться стороной или углом, без дыр.

Первые четыре метода ниже получают обычную линию из полностью закрашенных клеток. Ву дополнительно управляет их яркостью. Алгоритм окружности решает похожую задачу для кривой.

### Пошаговый алгоритм — спросить формулу в каждом столбце

Представь линейку, приложенную к клетчатому листу. В каждом столбце мы смотрим, на какой высоте проходит линейка, и закрашиваем ближайшую клетку.

Именно это делает уравнение **y = kx + b**. Число `k` — наклон: насколько меняется y при увеличении x на единицу. Число `b` определяет положение прямой по вертикали. По двум концам отрезка вычисляем `k = (y₁ − y₀)/(x₁ − x₀)` и `b = y₀ − kx₀`, затем перебираем целые x и округляем полученный y.

Например, у отрезка (0; 0) → (5; 2) наклон 2/5 = 0,4. В столбцах 0, 1, 2, 3, 4, 5 высоты прямой равны 0; 0,4; 0,8; 1,2; 1,6; 2. Ближайшие целые строки: **0, 0, 1, 1, 2, 2**.

**Почему работает:** уравнение даёт точное положение математической прямой, а округление выбирает ближайший центр в данном столбце. Отклонение по второй оси получается не больше половины клетки, если не учитывать погрешности вычислений. При вертикальном отрезке делить на `x₁ − x₀` нельзя; в нашей программе для крутых и вертикальных линий оси меняются ролями.

**Что запомнить:** каждый пиксель получаем новым вычислением по формуле. Предыдущий дробный y для следующего шага не нужен.

### ЦДА — использовать постоянную скорость движения по прямой

Если человек идёт по прямой с постоянной скоростью, то за равные промежутки времени он делает одинаковые перемещения. ЦДА использует эту идею для координат.

Отрезок делится на **L = max(|dx|, |dy|)** равных шагов. На каждом шаге к дробным координатам прибавляются одни и те же числа: `Δx = dx/L`, `Δy = dy/L`. Полученную точку округляем только для вывода пикселя. Внутри алгоритма продолжаем хранить дробные координаты.

На отрезке (0; 0) → (5; 2) прибавляем к x единицу, к y — 0,4. Получаем те же высоты 0; 0,4; 0,8; 1,2; 1,6; 2. Но теперь 1,2 получается как **предыдущее 0,8 + 0,4**, а не как новое умножение 3 · 0,4.

**Почему работает:** после i шагов координаты в точной арифметике равны `x₀ + i·dx/L` и `y₀ + i·dy/L`. Это точки исходного отрезка; после L шагов приходим ровно в его конец. Выбор L гарантирует единичный шаг по главной оси и шаг не больше единицы по другой.

Если бы мы после каждого шага заменяли внутренний y округлённым, дробная часть терялась бы. Например, 0 + 0,4 каждый раз округлялось бы обратно в 0 и линия не поднималась бы. Поэтому **дробную координату сохраняем, округлённую только рисуем**.

**Что запомнить:** ЦДА экономит повторные умножения, заменяя их сложениями. Но приближённо записанная дробь участвует во всех следующих шагах, поэтому её погрешность может накапливаться.

### Брезенхем для отрезка — следить, когда накопилось полклетки

Для объяснения возьмём линию вправо и вверх с наклоном от 0 до 1. В следующий столбец попасть нужно обязательно. Выбор только из двух клеток: **вправо** или **вправо-вверх**.

Представь, что идеальная прямая постепенно поднимается, а наша клетчатая линия некоторое время остаётся на одной строке. Когда идеальная высота следующего столбца достигает середины между текущей строкой и строкой выше, пора поднять пиксель. После подъёма на одну клетку накопленное отставание уменьшается на единицу.

Это можно было бы считать дробями. Пусть `h` — идеальная высота следующей точки относительно текущей строки. Тогда решение звучит так: **если h ≥ 0,5, идём по диагонали**. Брезенхем хранит ту же проверку в увеличенном масштабе: `e = 2·dx·(h − 0,5)`. Умножение на положительное число не меняет знак, поэтому условие превращается в **e ≥ 0**.

**Зачем именно 2·dx:** наклон содержит дробь `dy/dx`, а граница выбора — половину клетки. Умножение на `2·dx` убирает оба знаменателя. В результате можно считать только целыми числами, не меняя смысл решения.

Для первого перехода h = dy/dx, поэтому `e₀ = 2·dy − dx`. При продвижении вдоль прямой к e прибавляется `2·dy`. Если подняли пиксель на строку, из e вычитается `2·dx`. Так получаются правила из кода.

**Почему работает:** мы каждый раз проверяем, какая из двух соседних клеток ближе к идеальной высоте, но делаем это без вычисления самой дробной высоты. `e` — величина для принятия решения, а не расстояние в пикселях и не признак того, что алгоритм «ошибся».

Для линии вниз меняется знак шага по y, для движения влево — по x, для крутой линии оси переставляются. Логика «один обязательный шаг и один возможный» сохраняется.

**Что запомнить:** ЦДА накапливает дробную координату; Брезенхем накапливает целую величину, достаточную для выбора следующей клетки.

### Кастл–Питвей — собрать маршрут из повторяющихся узоров

Обычную растровую линию можно записать как маршрут: `s` означает шаг по главной оси, `d` — шаг по диагонали. Например, для линии вправо-вверх это (+1; 0) и (+1; +1).

Пусть после отражений и перестановки осей нужно пройти `a` клеток вправо и `b` вверх, где 0 ≤ b ≤ a. Всего должно быть **a ходов**, из них **b диагональных** и **a − b обычных**. Но одного количества мало: если сначала сделать все диагонали, а потом все обычные шаги, получится ломаная. Их нужно распределить вдоль маршрута так, чтобы он оставался около прямой.

Брезенхем получает такое распределение, принимая отдельное решение на каждом шаге. Кастл–Питвей использует структуру последовательности: строит её из коротких блоков. В нашей реализации сначала есть блоки `s` и `d`. Затем из большего числа в паре `(a − b, b)` вычитается меньшее, а блоки объединяются по правилам алгоритма; один из них при объединении читается в обратном порядке. Так короткие узоры превращаются в полный маршрут.

**Почему здесь возникает алгоритм Евклида:** вычитания находят общий размер повторяющихся частей. Например, перемещение (18; 15) состоит из трёх одинаковых перемещений (6; 5), потому что НОД(18, 15) = 3. Поэтому достаточно построить подходящий маршрут для одного периода и повторить его три раза.

**Почему получается прямая:** правила сборки задают порядок ходов, который удерживает путь около идеального отрезка; в этой реализации он совпадает с порядком Брезенхема. Повторение блока для (6; 5) продолжает линию с тем же наклоном 5/6. Важны и количества символов, и их расположение — произвольная перестановка ходов этот результат не сохранит.

Частные случаи совсем простые: b = 0 — только `s`, b = a — только `d`. После построения маршрута отражения и перестановка осей возвращают его в исходное направление.

**Что запомнить:** вместо выбора по ошибке у каждого пикселя сначала собираем строку ходов. Разные способы вычисления могут давать совершенно одинаковую картинку.

### Ву — показать дробное положение через яркость

Если линия проходит на высоте 2,2, обычный метод выбирает строку 2. Но по одному полностью закрашенному пикселю уже не видно, было ли точное положение 2,0 или 2,2. Когда округление переключается на следующую строку, получается заметная ступенька.

Ву сохраняет информацию о дробном положении с помощью двух соседних пикселей. Записываем высоту как **y = n + f**, где n — округление вниз, а f — остаток от 0 до 1. Пикселю на строке n даём вес **1 − f**, на строке n + 1 — вес **f**.

Например, при y = 2,2 нижний пиксель получает 0,8 цвета линии, верхний — 0,2. При y = 2,8 — наоборот. При движении прямой эти веса меняются постепенно, поэтому переход между строками выглядит мягче.

**Почему именно такие веса:** их сумма всегда 1, то есть общий вес линии в столбце не меняется. А средняя высота с учётом весов равна `n·(1 − f) + (n + 1)·f = n + f = y`. Значит, два пикселя вместе передают точное положение прямой, хотя каждый из них стоит в целой координате.

В нашей программе дробная часть вычисляется через деление с остатком, поэтому ошибка от последовательного сложения y не накапливается. Для крутых линий роли строк и столбцов меняются.

**Что запомнить:** Ву меняет способ отображения линии: вместо одного полностью закрашенного пикселя обычно выдаёт два с разными весами. Сглаживание достигается промежуточными оттенками.

### Брезенхем для окружности — выбирать шаг по уравнению круга

У окружности нельзя просто прибавлять один постоянный наклон: около верхней точки дуга идёт почти горизонтально, а ближе к боку становится крутой. Поэтому решение о следующей клетке нужно менять по мере движения.

Сначала строим небольшой участок: от верхней точки (0; R) до диагонали x = y. На этом участке достаточно каждый раз увеличивать x на единицу, а y либо сохранять, либо уменьшать на единицу. Снова есть всего два кандидата: **вправо** и **вправо-вниз**.

Чтобы оценить кандидата, используем уравнение окружности. Для центра в начале координат считаем **F(x, y) = x² + y² − R²**. На идеальной окружности F = 0, внутри F < 0, снаружи F > 0. Сравнение значений для соседних кандидатов позволяет выбрать тот, который лучше приближает дугу по этому критерию.

В нашей реализации величина решения — **d = F(T) + F(S)** для двух кандидатов следующего шага. Если d < 0, выбираем верхнего кандидата T, иначе — нижнего S. Когда кандидаты по разные стороны окружности, знак суммы показывает, у какого из них меньше модуль F. Если оба внутри, ближе к границе верхний; если оба снаружи — нижний. Это сравнение по уравнению окружности, а не точное измерение расстояния с помощью корня.

**Почему не считаем квадраты заново:** при переходе на соседнюю клетку квадрат меняется предсказуемо: `(x + 1)² − x² = 2x + 1`. Поэтому значение d можно обновлять добавлением небольших целых выражений. Отсюда берутся `4x + 6` и `4(x − y) + 10` в коде. В начале кандидаты (1; R) и (1; R − 1), поэтому `d₀ = 1 + (2 − 2R) = 3 − 2R`.

**Зачем считаем только одну восьмую:** если (x; y) лежит на окружности, то на ней лежат и точки с изменёнными знаками, и точки с переставленными x и y. Например, из (3; 6) получаем (±3; ±6) и (±6; ±3). Дальше диагонали x = y считать ту же дугу уже не нужно: она получится перестановкой координат. Для другого центра просто прибавляем его координаты к этим точкам.

**Что запомнить:** для окружности тоже выбираем между двумя соседями по целой величине решения. Но эта величина выводится из уравнения окружности, а восемь отражений позволяют вычислять только малую часть дуги.

## Почему выбран именно такой отрезок

Он идёт на 18 клеток вправо и на 15 вниз. Значит, на каждый шаг вправо точная прямая опускается на 15/18 = **5/6 клетки**. Её уравнение: **y = −5x/6**.

У пикселя целочисленные координаты обозначают **центр**. Например, клетка (3; −2) занимает по вертикали от −2,5 до −1,5. Красная линия — идеальная прямая, закрашенные квадраты — её приближение пикселями.

При **x = 3, 9 и 15** прямая проходит точно посередине между центрами двух соседних клеток. Например, при x = 3 получаем y = −2,5: до центра −2 и до центра −3 одинаковое расстояние 0,5. Это **ничья**. В таких местах алгоритмы могут выбрать разные клетки и оба результата будут допустимы.

В остальных столбцах у четырёх обычных методов пиксели совпадают. Все они строят по 19 пикселей: столбцы от 0 до 18 включительно.

| Где смотреть | Пошаговый | ЦДА | Брезенхем | Кастл–Питвей |
|---|---|---|---|---|
| x = 3, точное y = −2,5 | (3; −2) | (3; −2) | (3; −3) | (3; −3) |
| x = 9, точное y = −7,5 | (9; −7) | (9; −7) | (9; −8) | (9; −8) |
| x = 15, точное y = −12,5 | (15; −12) | (15; −13) | (15; −13) | (15; −13) |

## 1. Пошаговый — каждый раз подставляем x в формулу

**Что сказать:** «Беру очередной x, заново считаю y по уравнению прямой и округляю до ближайшего центра пикселя».

На нашем отрезке при x = 15: y = −5 · 15 / 6 = −12,5. Программа получает ровно −12,5 и использует правило **floor(y + 0,5)**: прибавляет половину, затем округляет вниз. Получается floor(−12) = **−12**. На трёх спорных местах выбирается верхняя из двух клеток.

В целом метод простой, но в цикле есть умножение дробного числа и округление. Каждый y считается независимо от предыдущего: ошибки от последовательного сложения не накапливаются. При этом сами дробные вычисления тоже могут иметь погрешность.

Если отрезок крутой, программа шагает по y и считает x. Иначе шаг по x мог бы перескакивать через несколько строк и оставлять дыры.

## 2. ЦДА — прибавляем одно и то же приращение

**Переключи с пошагового на ЦДА и смотри x = 15.** Клетка сдвинется с −12 на −13.

**Что сказать:** «ЦДА вместо нового умножения каждый раз прибавляет к прошлому y постоянное число −5/6. В точной арифметике получится то же самое. Но компьютер хранит эту дробь приближённо, и при сложениях погрешность накапливается».

На этом примере после 15 сложений хранится **−12.500000000000002**, то есть чуть ниже границы −12,5. После прибавления 0,5 и floor получается **−13**. У пошагового метода здесь было ровно −12,5, поэтому он выбрал −12.

При x = 3 ЦДА получает −2,5, при x = 9 — −7,499999999999999. Поэтому в этих двух местах ЦДА ещё совпадает с пошаговым методом.

Большая таблица округляет числа для удобства, поэтому может показывать одинаковые «−12,5» при разном результате. Полное значение для x = 15 написано в пояснении слева.

**Главное:** различие на рисунке здесь связано с конечной точностью `float`. Если считать точными дробями и одинаково решать ничьи, пошаговый и ЦДА дадут одинаковый результат. Нельзя говорить, что ЦДА всегда рисует другую линию или обязательно ошибается на целый пиксель относительно ближайшего допустимого центра.

## 3. Брезенхем для отрезка — выбираем по целой ошибке

**Переключи с ЦДА на Брезенхема и смотри x = 3 и x = 9.** Закрасятся нижние кандидаты. При x = 15 рисунок совпадёт с ЦДА.

**Что сказать:** «Брезенхем не хранит дробный y. Он хранит целое число, которое показывает, пора ли сделать шаг по второй оси. Поэтому в цикле нужны сложения и сравнение, без дробного округления».

У нас dx = 18, модуль dy = 15, шаг по y равен −1. Начальная ошибка:

```text
e = 2·15 − 18 = 12
```

После выдачи текущего пикселя программа готовит следующий: если e ≥ 0, уменьшает y на 1 и вычитает из e число 36. Затем всегда прибавляет к e число 30 и увеличивает x.

Первые переходы:

| Текущий пиксель | e до перехода | Решение | Следующий пиксель | Новое e |
|---|---|---|---|---|
| (0; 0) | 12 | вниз и вправо | (1; −1) | 12 − 36 + 30 = 6 |
| (1; −1) | 6 | вниз и вправо | (2; −2) | 6 − 36 + 30 = 0 |
| (2; −2) | 0 | вниз и вправо | (3; −3) | 0 − 36 + 30 = −6 |
| (3; −3) | −6 | только вправо | (4; −3) | −6 + 30 = 24 |

**e = 0 означает ничью для следующего пикселя.** Условие e ≥ 0 включает равенство, поэтому ничья разрешается в сторону конца отрезка — здесь вниз. Это даёт (3; −3), (9; −8), (15; −13).

В целом преимущество — целые вычисления и точное сравнение на границе. Но если поменять концы местами, направление разрешения ничьей тоже поменяется. Это свойство выбранного правила, а не поломка.

## 4. Кастл–Питвей — заранее строим последовательность ходов

**Переключи с Брезенхема на Кастла–Питвея. Рисунок останется тем же.** Покажи, что справа вместо ошибок теперь ходы `s` и `d`, а над ними — построение строки.

**Что сказать:** «Здесь другой способ получить тот же набор пикселей. Брезенхем на каждом шаге решает по ошибке, а Кастл–Питвей сначала строит строку обычных и диагональных ходов, затем исполняет её».

Для нашего отрезка:

- `d` — вправо и вниз: (+1; −1);
- `s` — только вправо: (+1; 0).

Нужно 18 ходов вправо, из них 15 с движением вниз. Алгоритм работает с парой (18 − 15; 15) = **(3; 15)**. Вычитания дают (3; 12), (3; 9), (3; 6), (3; 3). Параллельно из коротких строк собирается период **dddsdd**, который повторяется три раза:

```text
dddsdd | dddsdd | dddsdd
```

В одном периоде 6 шагов вправо и 5 вниз. Три периода дают нужные 18 и 15.

В этой реализации результат совпадает с Брезенхемом, включая ничьи. Поэтому обещать отдельную форму линии у каждого метода нельзя. Отличие здесь видно в вычислениях. Время Кастла–Питвея зависит от наклона: когда вычитаний и склеек строк много, он замедляется. Для дополнительного показа можно вручную задать (0; 0) → (10000; 1) и сравнить время с Брезенхемом; на сетке такой длинный отрезок рассматривать неудобно.

## 5. Ву — делим яркость между двумя клетками

Нажми «Для сдачи (пример)», затем выбери **Ву**. При необходимости увеличь сетку, чтобы видеть доли внутри клеток.

**Что сказать:** «Предыдущие методы выбирали одну клетку целиком. Ву распределяет яркость между двумя соседними клетками: ближняя получает больше, дальняя меньше. Так ступеньки становятся мягче».

При x = 3 точное y = −2,5. Поэтому (3; −3) и (3; −2) получают **по 0,5**. Аналогично при x = 9 и 15. Ву в этих местах не выбирает победителя ничьей, а показывает оба пикселя с половинной яркостью.

При x = 1 точное y = −5/6 ≈ −0,833. Ближе центр −1: клетка (1; −1) получает **5/6**, а (1; 0) — **1/6**. Сумма равна 1. Более того, среднее положение с этими весами точно равно −5/6.

Здесь «яркость» — вес цвета линии: 1 означает полный цвет, 0 означает белый фон. Чем вес меньше, тем клетка светлее. Это не буквальная яркость белого цвета.

Для отрицательных координат важно брать целую часть вниз: floor(−0,833…) = −1. Тогда дробная часть — 1/6, положительная. Усечение к нулю дало бы неправильные веса.

На нашем отрезке Ву выдаёт **34 пикселя с ненулевым весом**, обычные методы — 19. За сглаживание платим дополнительными вычислениями и закрашиванием соседей. Визуальная мягкость не означает, что обычные алгоритмы неверно выбрали свои пиксели.

## 6. Брезенхем для окружности — другая фигура и восемь отражений

Выбери **«Брезенхем (окружность)»**. Появится окружность с центром (0; 0), R = 7.

**Что сказать:** «У отрезка наклон постоянный. У окружности он меняется. Здесь алгоритм выбирает следующий пиксель дуги по отдельной целой ошибке и использует симметрию: считает только одну восьмую, остальные точки получает отражением».

Начинаем с (0; 7), d = 3 − 2R = **−11**. Кандидаты: вправо **T = (x + 1; y)** или вправо-вниз **S = (x + 1; y − 1)**.

- Если d < 0, берём T и прибавляем 4x + 6.
- Иначе берём S, прибавляем 4(x − y) + 10 и уменьшаем y.
- В обоих случаях увеличиваем x; в формулах используются x и y до перехода.

Первые переходы: (0; 7), d = −11 → (1; 7), d = −5 → (2; 7), d = 5 → (3; 6), d = −5.

Считаем до пересечения с диагональю x = y. Получаются шесть исходных точек: (0; 7), (1; 7), (2; 7), (3; 6), (4; 6), (5; 5). Каждую отражаем относительно осей и диагоналей: (±x; ±y), (±y; ±x). После удаления повторов на осях и диагоналях получаем **40 пикселей**.

Это отдельная задача. Переход от линии к кругу показывает назначение алгоритма окружности; он не доказывает, что этот алгоритм точнее алгоритма отрезка.

## Короткий ответ на защите

«На отрезке (0; 0) → (18; −15) есть три ничьи. Пошаговый считает y заново, ЦДА прибавляет приращение — из-за накопления погрешности у x = 15 они выбирают разные равноудалённые клетки. Брезенхем работает с целой ошибкой и решает ничьи в сторону конца отрезка. Кастл–Питвей строит тот же растр через строку ходов. Ву делит яркость между соседями и сглаживает ступеньки. Окружность Брезенхема использует другую ошибку и восемь отражений. Поэтому различия надо смотреть и на рисунке, и в таблице вычислений».

Если спросят про скорость: «Над таблицей измеряется время построения списка пикселей без рисования. Берётся лучшая серия из трёх, внутри неё усредняются повторные вызовы. На коротком примере порядок по времени может колебаться; сравнение длин приведено в отчёте.
